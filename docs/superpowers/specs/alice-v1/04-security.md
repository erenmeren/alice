## 14. Threat Model

Method: STRIDE per component, on the data-flow diagram below. Ratings are residual risk after the listed mitigations. Requirement IDs (SEC-nnn) refer to Section 15.

### 14.1 Assets

| ID | Asset | Why it matters |
|----|-------|----------------|
| A1 | Platform SSH private key (Ed25519) and all target credentials | Grants access to every managed server |
| A2 | Managed private keys (TLS keys, SSH keys generated by Alice) | Impersonation of servers/users |
| A3 | Azure Service Principal secrets/certificates | Read (and possibly import) access to customer Key Vaults |
| A4 | Master key (`/opt/alice/keys/master.key`) and recovery passphrase | Unlocks A1-A3 and backups |
| A5 | User accounts, TOTP seeds, recovery codes, API tokens, sessions | Control of the platform |
| A6 | Audit log | Evidence for KVKK/BDDK audits and forensics |
| A7 | Inventory metadata (hosts, users, cert names) | Reconnaissance value |
| A8 | License file, installation ID, high-water mark | Vendor revenue |
| A9 | Release artifacts and vendor signing keys | Integrity of what customers run |

### 14.2 Actors

| Actor | Capability assumed |
|-------|--------------------|
| External network attacker | Reaches port 443; may be MITM between Alice and targets/Azure/OIDC/SMTP |
| Unauthenticated internal user | Same as above, on the LAN |
| Malicious or compromised Operator | Valid session, Operator role |
| Malicious or compromised Admin | Valid session, Admin role (partially out of scope, see 14.5) |
| Compromised target host | Attacker controls a managed server (can return hostile data to Alice) |
| Host-level attacker | Root on the Alice host, or read access to its disk/volumes |
| Backup thief | Has an `alicectl backup` file or DB dump, no passphrase |
| Malicious customer | Owns the install and binary; wants to bypass the license |
| Supply-chain attacker | Compromises a dependency, base image, CI, or update tarball |

requests; may return hostile problem documents, renewal windows, chains and URLs) and a **hostile DNS hook** (the
administrator-configured HTTPS endpoint that publishes DNS-01 records; may answer slowly, hugely or with redirects). The
**Malicious or compromised Operator** can now also trigger an order, a Test run, a deployment and binding changes of an
existing ACME certificate, i.e. the renewal of names an Admin pre-approved; it cannot add names, change a provider or a
hook, or switch unattended deployment on.

(Amendment 2026-10-20, R46.) Key-compromise incidents: starting one and every action on one (retry, revoke now regardless, choosing the replacement, closing) is **Admin** with step-up, never a token (`certificates.incident`); reading incidents and the impact of a certificate is every role and `read` tokens, except the network discovery endpoints of an impact, which need `discovery.view`.

### 14.5 Top scenarios and explicit scope

1. **Platform compromise.** Alice holds credentials for all targets. Blast radius equals the union of the sudoers allowlists plus platform key access on every target. Mitigations reduce likelihood, not blast radius; documented in `SECURITY-REPORT.md` and customer hardening guide.
2. **DB/backup theft.** Covered by envelope encryption (DB) and passphrase encryption (backup).
3. **Malicious Operator.** Cannot download private keys, read audit log, change targets/policies, or view credentials. Can deploy certificates and add/remove keys to existing targets; every action audited.
4. **MITM.** TLS everywhere; SSH host key pinning; OIDC/Azure standard TLS.
5. **License bypass.** Accepted residual (Section 16).
6. **Supply chain.** Layered controls in 17.

Out of scope for v1: malicious Admin acting within granted powers; physical host compromise with live memory access; side-channel attacks; compromise of the customer IdP beyond group mapping controls.

## 15. Security Requirements

Each requirement is verifiable by an automated test (T), review (R), or configuration inspection (C), shown in brackets.

### 15.1 Authentication and passwords

- **SEC-001** Local passwords are hashed with Argon2id (`golang.org/x/crypto/argon2`, m=64 MiB, t=3, p=2, 16-byte random salt, 32-byte output), stored in PHC string format including parameters. [T]
- **SEC-002** Minimum password length is 12 characters, maximum 128; no composition rules; Unicode NFKC-normalized before hashing. [T]
- **SEC-003** Passwords are checked against a local breached-password list (top 100k, bundled as a Bloom filter or sorted hash file, no external calls); matches are rejected on set/change. [T]
- **SEC-004** Login errors are generic ("Incorrect username or password") and response time does not reveal account existence (dummy Argon2 verify for unknown users). [T]
- **SEC-005** Parameter upgrades: on login, if stored hash parameters are weaker than current, rehash. [T]

### 15.2 MFA

- **SEC-006** TOTP (`github.com/pquerna/otp`) per RFC 6238: SHA-1, 6 digits, 30 s, +/- 1 step window; the last accepted time step per user is stored and the same or earlier step is rejected. [T]
- **SEC-007** TOTP seeds are 160-bit random values stored envelope-encrypted; shown once as QR + text during enrollment; enrollment is not complete until a valid code is entered. [T]
- **SEC-008** 10 single-use recovery codes (80-bit, Argon2id-hashed) are issued at enrollment; regeneration invalidates the old set and requires MFA. [T]
- **SEC-009** MFA is mandatory for all local accounts; a local user cannot obtain a full session without completing it. For OIDC users MFA is delegated to the IdP (documented customer requirement); step-up for sensitive operations still applies to them where the operation is available to their role. Step-up (re-prompt within 5 minutes) is required for: private key download, user/role changes, SSO configuration, license upload, backup/restore, target credential change, rotation policy enabling, API token creation. [T]

### 15.3 OIDC

OIDC SSO is delivered in Phase 7 ("Alerts, dashboard and SSO", R31); Phase 1 is local authentication + TOTP only. Requirements below apply from Phase 7.

- **SEC-010** Authorization Code flow with PKCE (S256) only; implicit and hybrid flows are not implemented. [T]
- **SEC-011** `state` (256-bit random) and `nonce` (256-bit) are generated per login, bound to a short-lived (10 min) server-side record and browser cookie; single use; mismatches abort. [T]
- **SEC-012** ID token validation: signature via issuer JWKS (cached, refreshed on unknown `kid` with rate limit), `alg` restricted to RS256/ES256/PS256, `iss` exact match to configured issuer (discovery document issuer must also match), `aud` contains client ID, `azp` checked when multiple audiences, `exp`/`iat`/`nbf` with 60 s leeway, `nonce` match. [T]
- **SEC-013** Discovery and JWKS URLs must be HTTPS; redirect URI is exact-match configured; issuer/endpoints are fixed at configuration time by an Admin, not taken from the request. [T]
- **SEC-014** Group claim mapping: Admin configures claim name and a table `group value -> role`; user gets the highest mapped role; users with no mapped group are denied (no default role); the mapped role is capped at Operator unless the Admin setting "SSO users may be Admin" (default OFF) is enabled; role is re-evaluated at every SSO login; group changes take effect at next login; Entra "groups overage" (`_claim_names`) is handled by Graph lookup only if configured, otherwise login is denied with a clear message. [T]
- **SEC-015** SSO users are identified by (`iss`, `sub`), never by email; the wizard-created local admin cannot be converted to SSO or disabled by SSO, and the last enabled local Admin cannot be disabled, deleted or demoted. [T]

(Phase 7, R42: built as R42 items 18 to 24 — `POST` start and step-up routes, the `GET` callback as the one A-06 exception, the binding cookie `__Host-alice_oidc`, providers and endpoints fixed at configuration time and switched off when created, the key set bounded and expired by its cache headers, `client_secret_basic` only; users are matched by provider and subject (`oidc_provider_id`, `oidc_subject`), never by e-mail; the Entra overage is refused without a Graph lookup (`ALC-SSO-0007`); an SSO sign-in opens the step-up window only when the ID token's `auth_time` is at most 5 minutes old, SSO users cannot create API tokens; the role is re-evaluated at every sign-in and step-up, and switching "SSO users may be Admin" off demotes SSO Administrators to Auditor; the tests are the O-suite of `internal/auth/oidc` and `TestOIDCNegativeSuiteOverTheWire`; the review is `docs/security/reviews/phase-7.md`.)

`access.manage`: **Admin** (global) with step-up, never a token, ClassAlways.

- **SEC-027** (R53) Grants are read on every request with the session or the token (SEC-017): the global role and every
  role binding of the person, an environment binding expanded to the services that carry it at that request, an SSO or
  directory user's Administrator binding counted as Operator while "SSO users may be Admin" is off. A token acts with its
  owner's grants as they are now, narrowed by its scope; it is valid while some grant allows its scope. The reach of a
  permission (every service, or the services of the grants whose role allows it) filters every list, count, export, the
  dashboard and the discovery summary inside their queries, before paging. The break-glass account always keeps a
  global role (00028 CHECK, `ALC-USR-0004`). [T]
- **SEC-028** (R53) Every route that names a resource in its path declares a resolver (startup refuses one without); a
  caller with role bindings is checked against the resource before the handler runs: a resource it cannot see answers
  exactly as an absent one (the route's 404, audited `authz.denied` reason `out_of_scope`), one it sees but holds no
  right on 403 `ALC-AUTH-0002` (reason `scope`). Cross-service actions need the permission on every destination service
  (`ALC-SVC-0012`, counted, never named); a create into a service outside the reach is `ALC-SVC-0006`. Detail answers
  leave related rows of other services out and count them (`hidden_count`); a service outside the reach shows as
  `{"outside": true}`. Generated test: `TestScopedIDOR`. [T]
- **SEC-108** (R54, R49 Phase 3) Directory groups, automation accounts and limited tokens. (a) Every SSO and directory
  sign-in and step-up stores the user's groups (the first 1000 storable values; more are dropped and audited
  `user.groups_truncated`) in its transaction; the role bindings of a directory group of the user's own provider or
  directory whose value is among them count as the user's (SEC-027), capped at Operator for Administrator while "SSO
  users may be Admin" is off. A user without a mapped group signs in only when a binding reaches them; otherwise the
  refusal is `no_access` as before, which ends the user's sessions, revokes their tokens and forgets their groups. (b)
  An automation account (`auth_source = 'automation'`) has no password and never a global Administrator role (CHECK);
  no session, TOTP or recovery code can be stored for it (migration `00029`, SQLSTATE Z1029); the password form answers
  its name as an unknown one; only a global Administrator with step-up makes, changes and disables it and makes and
  revokes its tokens (`access.manage`, never a token); disabling revokes its tokens for good. (c) A token may be
  limited to 1 to 50 services its owner holds a role on: its rights are the owner's grants now ∩ its scope ∩ those
  services; the global role becomes a grant on them, so no platform route passes (`ALC-AUTH-0002`), whoever the
  owner. [T]
- **SEC-109** (R56, R49 Phase 4) Service owners and e-mail routing. (a) Ownership grants no access: owners are only
  e-mail recipients and are named on the service; a service's owners are replaced by a global Administrator only
  (`services.manage`, step-up, never a token), audited with what was added and removed; an automation account is never
  an owner. (b) A service's e-mails reach only the recipients of the services they concern (the Administrators while a
  policy keeps them, the owners, the policy's addresses); a member of an owner group receives them only while enabled,
  of the group's own provider or directory, and in the group at the last sign-in or step-up. (c) The platform e-mails
  (license, backup, sign-in block, audit chain, a tampered job, the test e-mail) go to the Administrator recipients only,
  through a notifier that cannot reach an owner. (d) Whether a role of an owner reaches the service is answered to a
  global `users.read` only. [T]
- **SEC-110** (R65) Canary deployment. (a) The application check of a canary dials only a managed location's own
  address, through the SEC-065 rule on the connected address, compares the served leaf with the deployed certificate
  before it sends a byte, and follows no redirect and no proxy (CN-1). (b) Skipping the canary ("Deploy to all at once")
  and releasing wave 1 early (Continue now) need a fresh step-up in a browser session and are refused to API tokens;
  Abort needs neither, and works in lock (CN-4). (c) The revert of a held wave-1 deployment reads the rollback guard
  (R48) first (CN-3). [T]

### 15.5 Sessions, CSRF, rate limiting

- **SEC-018** Session ID is 256-bit from `crypto/rand`; only its SHA-256 is stored server-side. Cookie: `__Host-alice_session`, HttpOnly, Secure, SameSite=Strict, Path=/, no Domain. [T]
- **SEC-019** Idle timeout 30 min, absolute lifetime 12 h; session ID regenerated on login and on privilege step-up; logout and password change revoke server-side; Admin can revoke any session. [T] (R39 items 1 and 5: only a person's activity — a state-changing request or a same-origin read marked `X-Alice-Activity: 1` — slides the idle timeout; an administrator's password reset and sign-out-everywhere also revoke the user's API tokens.)
- **SEC-020** Login rate limiting: per IP 10 attempts/min; per account, after 5 consecutive failures a progressive delay (1, 2, 4, ... up to 60 s) applies and after 10 a 15 min temporary lockout (never longer than 15 min); lockout events are audited and notify Admins (the notification email arrives with the notify module in Phase 7; R35); lockout does not apply to the host-root CLI reset. A failure counts toward the delay and lockout whether the password or the MFA code (or a step-up code, or the current password on password change) was wrong; the consecutive-failure counter resets after a completed sign-in (password and MFA code) or a successful step-up, never after a correct password alone. A failure recorded after a lockout has ended starts a new consecutive count (prod-readiness AUTH-1): the lockout is a ceiling of 10 evaluated guesses per 15 minutes, not a permanent state. [T]
- **SEC-021** General API limit: 300 requests/min per session and 60/min per IP for unauthenticated routes, `429` with `Retry-After`. Limits are in-memory token buckets; `X-Forwarded-For` is honored only from configured trusted proxies. [T]
- **SEC-022** Expensive endpoints (private key download, MFA verify, backup) have stricter limits (5/min). [T]
- **SEC-023** Request bodies capped at 1 MiB (10 MiB for certificate/license upload); server `ReadHeaderTimeout` 10 s, `ReadTimeout` 30 s, `WriteTimeout` 60 s, `IdleTimeout` 120 s. [T, C]
- **SEC-024** CSRF: every non-GET request requires header `X-CSRF-Token` matching a per-session token (HMAC of session ID) and must pass `Origin`/`Sec-Fetch-Site` checks (same-origin only); GET endpoints never mutate. [T]
- **SEC-025** API tokens authenticate via `Authorization: Bearer` only, are exempt from cookie CSRF but never accepted via cookie; tokens cannot perform MFA-step-up operations (private key download, user management, license, backup) and can never retrieve private keys in v1. [T]
- **SEC-026** API tokens: 256-bit random with `alice_` prefix, SHA-256 stored, scopes (read, operate), mandatory expiry (max 365 days), last-used timestamp, revocable, shown once. [T]

### 15.7 Secrets handling and cryptography

- **SEC-040** Envelope encryption: each secret gets a random 256-bit DEK; payload encrypted with AES-256-GCM (`crypto/aes`, `crypto/cipher`, 96-bit random nonce from `crypto/rand`); DEK wrapped with the master key via AES-256-GCM. Stored: `key_version`, wrapped DEK, nonces, ciphertext. [T]
- **SEC-041** AAD binds each ciphertext to its location. Payload layer: `table || '/' || row_id || '/' || column`. DEK-wrap layer: the same string plus `'/' || key_version`. Master-key rotation re-wraps only DEKs (recomputing the DEK-wrap AAD with the new version) and never touches payload ciphertext; moving ciphertext between rows or columns fails to decrypt. [T]
- **SEC-042** Master key: 256-bit from `crypto/rand`, file mode 0400 (default `/opt/alice/keys/master.key`, path configurable e.g. separate mount), owned by the container UID, on a separate volume from PostgreSQL data; customer docs require full-disk encryption; the process refuses to start if permissions are wider. Master key rotation (`alice keys rotate-master`, dry-run available, MFA step-up) re-wraps DEKs without re-encrypting payloads and creates a new `key_version`. [T]
- **SEC-043** Sub-keys are derived from the master key with HKDF-SHA256 (Go standard library `crypto/hkdf`, R35) using distinct `info` labels (`alice/hwm/v1`, `alice/job/v1`, `alice/csrf/v1`) (`alice/audit-hmac/v1` is reserved and unused: the audit chain is unkeyed in v1, KI-05); the master key itself is never used directly for MAC. [T]
- **SEC-044** Private keys are decrypted only in the provider call that needs them, held in `[]byte` wrapped in a `Secret` type that redacts on format/JSON/log and is zeroed after use. [T, R]
- **SEC-045** Private key download requires role Admin, fresh MFA step-up, a reason of at least 10 characters, is rate limited, audited (key ID, reason, IP), and the response carries `Cache-Control: no-store`. Optional passphrase-protected PKCS#8 export. [T]
- **SEC-046** Key generation: SSH Ed25519 by default (`crypto/ed25519`, RSA >= 3072 selectable); TLS keys ECDSA P-256 default, RSA >= 3072, RSA < 2048 rejected; all from `crypto/rand`. [T]
- **SEC-047** Approved primitives only: AES-256-GCM, ChaCha20-Poly1305 (SSH), Ed25519, ECDSA P-256/P-384, RSA >= 2048 (verification) / 3072 (generation), SHA-256/384/512, HMAC-SHA256, Argon2id, HKDF. MD5, SHA-1 (except TOTP), 3DES, RC4 and DSA are forbidden and grep-checked in CI. [T]
- **SEC-048** Backup encryption is hybrid (R4). The wizard generates an X25519 backup key pair; the public key is stored on the host; the private key is stored ONLY wrapped by the recovery passphrase (Argon2id m=64 MiB, t=3, p=4, 16-byte salt, AES-256-GCM) and embedded in each backup file, so the host never stores the passphrase or a passphrase-derived key. Each backup uses an ephemeral X25519 key agreement to the public key, HKDF-SHA256 to a file key, and encryption in 64 KiB chunks with AES-256-GCM, nonce = 4-byte random prefix || 8-byte counter, AAD includes header and final-chunk flag (prevents truncation/reorder). Header: magic `ALICEBK1`, version, ephemeral public key, wrapped private key + KDF params + salt. Restore = file + passphrase. [T]
- **SEC-049** Constant-time comparison (`crypto/subtle`) for tokens, MACs and hashes. [R]

(Amendment, ACME issuance 2026-10-13, a deviation recorded in `docs/superpowers/rulings/acme-issuance.md`; review `docs/security/reviews/acme-issuance.md`.) New sealed secrets under SEC-040/041: `acme_accounts/<id>/key` (ECDSA P-256 account key, generated by
Alice), `acme_providers/<id>/eab_hmac`, `acme_hooks/<id>/secret`, and the pending order key
`acme_orders/<id>/pending_key` (deleted when the order ends; on success moved into `managed_private_keys` in the same
transaction as the `certificates` row). Only the DER `secrets.Plaintext` is zeroed; Go's `ecdsa`/`rsa` key objects
cannot be, so their lifetime is kept to the order function. None of these values is returned by the API, written to a
log, an audit row, a job payload or an error (SEC-051's suite covers them: `TestACMESecretsNeverLeak`).

(Amendment, R59 deployment targets groundwork 2026-10-21; rulings `docs/superpowers/rulings/deployment-targets-groundwork.md`.)
New sealed secrets under SEC-040/041: an API target's credential (`credentials/<id>/ciphertext` with purpose `f5_device`
or `kubernetes_cluster`: a password, a ServiceAccount token or a client key; the user name and the client certificate

### 15.10 Audit log

- **SEC-070** Every authentication event, authorization failure, and mutating operation writes an audit row: `id`, `ts` (UTC, from server clock and the high-water-corrected clock), `actor`, `actor_ip`, `action`, `object`, `result`, `details` (redacted JSON), `prev_hash`, `hash`. [T] (R39 item 4: repeated authorization and license refusals of one person, permission, reason and route are written once per 10 minutes, and the count of the left-out ones in an appended summary row.)
- **SEC-071** `hash = SHA-256(prev_hash || canonical_json(row without hash))`. Rows are inserted inside a transaction that takes an advisory lock before reading the chain head, which serializes chain order (Phase 1 runs this under READ COMMITTED, which sees the latest head once the lock is held; R35). - **SEC-072** `alicectl audit verify` and a daily job re-verify the entire chain; a break raises a critical alert (banner, email, syslog). The chain head hash is included in every daily backup and in syslog forwarding, and the dashboard shows the daily audit head hash for offline recording. The wizard strongly recommends configuring syslog/SIEM forwarding. [T]
- **SEC-073** Optional forwarding to syslog (RFC 5424 over TLS TCP; UDP allowed only when explicitly chosen) and JSON webhook. Forwarding is asynchronous from a local outbox; failures are retried and surfaced in the UI; events are forwarded in chain order with `hash` included so the SIEM holds an independent copy. [T]
- **SEC-074** Audit rows are retained indefinitely in v1; there is no pruning (audit pruning with signed checkpoints is deferred to v2, R16). [T]
- **SEC-075** Audit export (CSV/JSON) is Admin/Auditor only, itself audited, and includes verification status. [T] (R39 item 7: the CSV carries it as a `# alice audit export: …` first line; one verification or export at a time, `ALC-AUD-0001`.)

## 16. License Protection

### 16.1 Goals and non-goals

The license mechanism must (a) prevent casual tampering, sharing between installations and trivial extension of validity, (b) never harm a paying customer (no false lock, no data loss), (c) work fully offline. It is not DRM: a motivated customer with the binary can bypass it (16.6). Goal (b) includes not turning a lapsed license into certificate outages at once: for 45 days after a licensed lock begins, certificates already managed keep renewing and deploying automatically (the continuity window, R44, §8.6); the license still ends everything else at the lock, and the window itself at its end.

### 16.2 File format (version 1)

A license file `alice.license` is UTF-8 JSON:

```json
{
  "format": 1,
  "key_id": "vk-2026-01",
  "payload": {
    "license_id": "LIC-2026-000123",
    "customer": "Example Bank A.S.",
    "installation_id": "ALICE-7F3K-9Q2M-XD41-B8TC",
    "issued_at": "2026-09-29T09:00:00Z",
    "valid_from": "2026-09-29T00:00:00Z",
    "valid_until": "2027-09-29T00:00:00Z",
    "max_targets": 100,
    "features": [],
    "format": 1
  },
  "signature": "base64url(Ed25519 signature, 64 bytes)"
}
```

- Signed bytes: `"ALICE-LICENSE-v1\n" || canonical(payload)`. The ASCII prefix is a domain separator so a signature can never be valid in another context (e.g., release manifests).
- **Canonical JSON:** RFC 8785 (JCS): keys sorted by UTF-16 code unit, no insignificant whitespace, ES6 number formatting (only integers are used in v1), strings NFC-normalized by the issuer. All timestamps are RFC 3339 UTC with `Z`. Verifier parses the payload, re-canonicalizes it and verifies against the re-serialized bytes, never against the raw file bytes, so whitespace differences do not matter while unknown-field injection is impossible (unknown fields are included in canonicalization and therefore signed, but rejected in format 1 to keep parsers strict; the only optional field beyond the example is `replaces`, used by correction licenses).
- **Format versioning:** `format` is present both outside (to select verifier) and inside the signed payload (to prevent downgrade). A binary supports formats `<= N`; a license with higher format shows "please update Alice" and keeps the previous valid license active. Additive changes go in new formats; v2 license-server distribution reuses the identical signed file.
- `features` is an array of strings; unknown features are ignored (v1 never reads it for gating).

### 16.3 Verification procedure

1. Reject file > 64 KiB; parse JSON strictly (no duplicate keys, no unknown top-level fields).
2. Select public key by `key_id` from the embedded key set (16.7); unknown key ID leads to "license was issued by an unknown key, contact support".
3. Verify `ed25519.Verify` over the domain-separated canonical bytes. Failure leads to reject; the previously active license is untouched.
4. Check `installation_id` equals the local installation ID (16.4).
5. Check `valid_from <= valid_until`, `issued_at <= valid_from + 24h`, `max_targets` in [1, 100000].
6. Evaluate time with the trusted clock (16.5): `now_trusted >= valid_from` and compute state instant-based in UTC (R25): ACTIVE while `now < valid_until`; GRACE while `valid_until <= now < valid_until + 168h`; LOCK afterwards. Warnings at 60/30/14/7/1 days remaining are computed from `valid_until`.
7. Persist the accepted license (raw file plus parsed metadata) in `license` and append to `license_status_history`; audit `license.uploaded`.

A newer `issued_at` for the same installation replaces the old one; uploading an older license than the active one is rejected unless it has a later `valid_until` or is a correction license (`replaces` names the license it supersedes; it may have an earlier `issued_at`).

### 16.4 Installation ID binding

- Installation ID has the format `ALICE-XXXX-XXXX-XXXX-XXXX` (random, Crockford base32 groups, the last character being a check digit) generated at first start, so typos are detected when the customer emails it. The installation timestamp is stored with it; the 30-day evaluation runs from that timestamp, is not reset by restore, and ends directly in LOCK without grace (R1, R27).
- It is stored in the DB (`settings`) and included in every backup; `alicectl restore` preserves it, so disaster recovery to new hardware keeps the license valid.
- It is deliberately not derived from hardware (VM cloning, host replacement, and container moves would lock legitimate customers). The trade-off is that a customer can clone the whole installation (DB and master key) and run two copies. This is accepted; the license file states the customer name and it is visible in the UI and audit exports.

### 16.5 Clock high-water mark

Purpose: make trivially setting the system clock backward ineffective against expiry.

- **Trusted time** `T = max(system_time, hwm)`.
- **Storage:** a record `{v:1, hwm: <unix seconds>, seq: <counter>, mac}` (written on the hourly tick) stored in two places: table `settings` (key `time.hwm`) and file `/opt/alice/state/hwm.dat` on the data volume. On start the larger valid `hwm` of the two wins; either being missing or invalid falls back to the other; both missing (fresh install or deletion) sets `hwm = max(system_time, build_time_of_binary)` and raises a warning "time reference reset" audited as such. Binary build time is embedded at compile time so an older `hwm` can never be earlier than the release.
- **MAC:** `HMAC-SHA256(K_hwm, "v1" || hwm || seq)` where `K_hwm = HKDF-SHA256(master key, info="alice/hwm/v1")`. The payload is also AES-GCM-encrypted with a sub-key so casual editing is not obvious (confidentiality is a convenience; integrity is the MAC). Invalid MAC is treated as missing (never as valid) and audited.
- **Update cadence:** in-memory `T` checked continuously; persisted at start, hourly, on every license evaluation, and on graceful shutdown; only ever increases.
- **Rollback behavior:** if `system_time < hwm - 5 min`, Alice uses `hwm` for all license math, shows an admin warning "the server clock appears to be behind (last seen <time>)" and audits `clock.rollback_detected` once per day. It does not lock. (R36: the warning appears beyond 65 minutes, L-52; while the clock is behind, the HWM advances with monotonic uptime, so license time never stands still; forward-jump detection is measured from the later of the last wall time and the HWM.)
- **Certificate notBefore evidence (R28):** certificate `notBefore` values are NOT used in license math, so a far-future `notBefore` on a hostile target can never lock the platform. If discovered/imported certificates have `notBefore` clearly in the future relative to the system clock, Alice only raises an admin warning "system clock appears to be behind".
- **Forward jump (R26):** a jump is suspicious if the wall clock advanced more than 48 h more than monotonic uptime since the last hourly hwm tick. A suspicious jump raises an admin warning ("clock jumped forward by X days") and is audited; the new time may trigger GRACE/LOCK transitions only after 24 h of monotonic uptime at the new time, after which it is accepted. This gives the admin time to fix the clock or request a correction license (`replaces` field).
- The hwm can be cleared or reset by a customer who has the master key (they can recompute the MAC). This is accepted (16.6).

### 16.6 What cannot be prevented, and why that is acceptable

- **Binary patching, LD_PRELOAD, memory patching, running a modified build.** The customer controls the machine and receives the executable; any check can be removed by someone who can edit machine code. Go compiled code with no symbols makes casual patching harder, but not impossible. No obfuscator or anti-debug measure is planned: they add fragility and false positives on customer servers, and would complicate security review by regulated customers who audit what runs in their datacenter.
- **Replacing the embedded public key** with their own and self-signing. Same category as patching.
- **Clock manipulation combined with deletion of hwm** and knowledge of the master key. (R39 item 2: the lock gate no longer trusts a stale evaluation; R39 item 6: a missing or removed installation seal is always tampering; what remains for someone who holds the master key and the database is listed there.)
- **Cloning the installation** to run copies.
- **Why acceptable:** (1) The target market is regulated enterprises and MSPs with contractual, legal and audit relationships with the vendor; they need vendor support, updates, and security fixes, and using a patched binary voids all of it and breaks their own compliance posture. (2) Casual violations (sharing a license file, editing JSON, clock rollback, exceeding target count) are prevented or made visible. (3) Aggressive DRM would risk locking paying customers, which costs more than piracy for a solo vendor. (4) Contractual license terms and audit rights cover the rest. (5) Exceeding the limit only blocks adding targets; even a bypass yields a small revenue impact per customer.

### 16.7 Vendor signing key protection

- **Keys:** a **license signing key** (Ed25519) is separate from the **release signing key** (SEC-107); compromise of one must not compromise the other. Each key has a `key_id` (`vk-YYYY-NN`).
- **Generation:** on an air-gapped, freshly installed offline machine (live USB, no network), using `licensectl keygen` (Go stdlib `crypto/ed25519`, `crypto/rand`). The private key is written encrypted (Argon2id + AES-256-GCM, passphrase of >= 6 random Diceware words) to two hardware-encrypted USB drives; alternatively held on a YubiKey/HSM-backed PKCS#11 device when the vendor buys one.
- **Storage:** primary in a fireproof safe on the vendor premises; second encrypted copy in a bank safe deposit box or notary; the key itself also has a paper backup, the passphrase is written on paper stored separately from the drives, plus a sealed copy with a trusted second person (Shamir 2-of-3 split via `licensectl keygen --split` when more than one trusted person exists). The signing key is never on a laptop connected to the internet, in CI, in cloud storage, or in a password manager sync.
- **Issuing licenses:** `licensectl issue` runs only on the offline signing machine or on a dedicated hardened laptop that is offline while the key is mounted; licenses are transferred out via a clean USB stick. `licensectl` keeps a signed, append-only issuance log (license_id, customer, installation_id, dates, targets) for reconciliation and revocation decisions.
- **Backup and recovery test:** yearly, decrypt the backup on a clean machine and sign a test payload verified by a released binary.
- **Key rotation via multiple embedded public keys:** the binary embeds a set `{key_id: public_key, status: active|retired}`. New releases add the next key ahead of time (at least one release before it's used). Licenses name the signing `key_id`. Retiring a key means removing it from a later release; existing licenses signed with it remain valid only on releases that still embed it, so retire only after all licenses using it have expired or been reissued. A compromised key is marked `revoked` in a release's revocation list (`key_id` and optional `issued_before` cutoff); the vendor then reissues licenses to customers under the new key, free of charge.
- **Compromise procedure:** (1) generate new key offline, (2) ship an emergency release embedding new key and revoking old, (3) reissue all active licenses, (4) notify customers per 17.4. Since the public key is embedded, a leaked private key allows anyone to mint licenses until the revocation ships, hence the offline rules above.
- **Release key note:** releases are signed by a separate key handled with the same procedure, and the release process (17.5) requires a human at the offline machine.

## 17. Secure Development Process & Release Checklist

### 17.1 CI security tooling

| Tool | Scope | Gate |
|------|-------|------|
| `gofmt`, `go vet`, `staticcheck` | Go code quality and bug patterns | Fail on any finding |
| `gosec` | Go security lint (G101 secrets, G201/G202 SQL, G304 file paths, G402 TLS, G401/G501 weak crypto, G204 exec) | Fail on medium+ unless annotated `#nosec` with reason reviewed in PR |
| `govulncheck` | Reachable vulnerabilities in Go modules and stdlib | Fail on any reachable vuln with a fix |
| `npm audit --omit=dev`, `osv-scanner` (go.sum, package-lock) | JS and Go dependency CVEs | Fail on High/Critical |
| ESLint (`security`, `react`, `no-danger`) | SPA XSS patterns | Fail |
| Trivy `fs` and `image` | Dependencies, OS packages in images, misconfig of Compose/Dockerfile | Fail on High/Critical with fix |
| `gitleaks` | Secrets in diff and full history | Fail; also as pre-commit hook |
| `syft` | SBOM (CycloneDX JSON) for binary and images; `grype`/Trivy consumes it | Artifact attached to the release |
| `testssl.sh` | TLS configuration of running container | Fail on grade below A |
| OWASP ZAP baseline | Passive scan of running app | Fail on medium+ new alerts |
| `go test -race -fuzz` (short) | Fuzz for parsers, command builder, canonical JSON | Fail on crash |
| `cosign` or minisign signature check | Release artifacts signed after build | Release only |

CI additionally: pinned action versions by commit SHA, least-privilege CI tokens, protected `main`, mandatory PR review, signed tags, and no long-lived secrets in CI (the license and release signing keys are never in CI).

### 17.2 Security review gates per phase

| Phase | Security review focus | Exit criteria |
|-------|----------------------|---------------|
| 0 Skeleton & CI | CI tooling wired, headers/CSP baseline, container hardening | All scanners run green; hardened compose passes Trivy misconfig |
| 1 Core auth (local + TOTP)/RBAC/audit/secrets | Crypto design review, session/CSRF, MFA, envelope encryption, audit chain, redaction | Authz matrix test passes; leak test passes; audit chain verify; peer crypto review sign-off |
| 2 Licensing | Signature verification, canonicalization, hwm MAC, fake-clock tests, lock behavior safety | Tamper/forgery/downgrade tests; no data loss on lock |
| 3 Provider framework + SSH | Host key TOFU/change handling, command allowlist, sudoers, injection fuzzing | Fuzz corpus clean; changed host key blocks all ops |
| 4 Nginx | Atomic deploy, rollback, path validation, private key handling | Fault-injection tests (bad cert, failed reload, connection drop) leave server unchanged |
| 5 Azure | Least privilege, credential storage, TLS, throttling | Mock and real-suite tests; no secret contents read beyond scope |
| 6 SSH key lifecycle | Never remove last access, own-key protection, overlap logic | Rotation failure-injection tests; platform key cannot be removed |
| 7 Alerts, dashboard and SSO | OIDC flow (SEC-010..015), Email header injection, output escaping, notification content leaks | OIDC test suite passes; no secrets in emails; XSS tests on all rendered strings |
| 8 Packaging & release | Installer, update script, signature verification, backup/restore, full pen-test pass | Release checklist (17.7) complete; `SECURITY-REPORT.md` signed off |

Each gate produces a short review note stored in `docs/security/reviews/phase-N.md`; findings rated High block phase exit.

### 17.3 Security test types

1. **Authorization matrix test:** role x endpoint x method generated from OpenAPI; asserts allow/deny for Admin/Operator/Auditor/unauthenticated/API-token scopes.
2. **Secret-leak-to-log test:** canary secrets (SEC-051).
3. **Rate-limit and lockout tests:** login, MFA, download, API.
4. **Session tests:** idle/absolute expiry, fixation, revocation, cookie flags, CSRF failure cases.
5. **OIDC tests** (Phase 7) against a Keycloak container: wrong issuer/aud/nonce/state, expired token, bad signature, missing PKCE, group mapping edge cases.
6. **Crypto tests:** known-answer tests, tampered ciphertext, swapped rows (AAD), truncated/reordered backup chunks, wrong passphrase.
7. **Audit tests:** chain verification, tamper detection after row update/delete, restore continuity.
8. **License tests:** forged signature, altered field, wrong installation ID, wrong `key_id`, replayed old license, clock rollback and jumps with fake clock, hwm MAC tamper.
9. **Injection/fuzz tests:** SQL, command builder, path validation, PEM/PKCS#12 parsers, JSON canonicalizer.
10. **Failure-injection tests** on deployment and rotation (network drop mid-write, `nginx -t` failure, reload failure, handshake mismatch).
11. **Container tests:** run as non-root, read-only FS, no published DB port, dropped capabilities.
12. **Backup/restore test:** backup, wipe, restore, verify data, license, audit chain (every release).
13. **External penetration test** before 1.0 and after any major auth change (vendor-commissioned).

### 17.4 Vulnerability disclosure and customer notification

- `SECURITY.md` and `security.txt` on the vendor site: contact `security@<vendor-domain>` with a published PGP key, safe-harbor statement, acknowledgment within 3 business days, triage within 7 days.
- Severity per CVSS v3.1/4.0; targets: Critical fix within 14 days, High within 30, Medium within next minor release.
- Advisories are published as signed files (`ADVISORY-YYYY-NNN.md`) listing affected versions, impact, fix version, workaround, CVE if assigned; delivered by email to registered customer security contacts and posted on the vendor site (air-gapped customers receive them by email with attachment and in the update package `advisories/` folder).
- Each release includes a "Security fixes" section in release notes; Critical fixes ship as patch releases with the same update path.
- Alice shows, from local data only (no telemetry), a banner if the installed version is listed in a bundled advisory file after an update that adds a newer advisory list.
- Coordinated disclosure: 90 days default before publication of researcher findings; credit given.

### 17.5 Release process (signing)

1. Tag reviewed commit (signed). 2. CI builds reproducibly, runs all gates, outputs tarball, images, SBOM, `SHA256SUMS`. 3. A human transfers `SHA256SUMS` to the offline machine and signs it with the release key. 4. Signature is added to the release artifacts; `install.sh` embeds the release public key. 5. Release published; checksum and signature also posted on the vendor site and emailed to customers, together with the release public key fingerprint (also published on the vendor website and in the license delivery email, R20).

The package's `helper/` folder carries the helpers for the managed servers, the Linux `alice-helper` (amd64, arm64) and the Windows `alice-helper.exe` (`alice-winhelper-windows-amd64.exe`, `-arm64.exe`), each set with its checksum file, all listed in the signed `SHA256SUMS`; `release.yml` stages a tag only after the real-Windows check passed on it (R63).

### 17.6 `SECURITY-REPORT.md` structure

1. Document metadata (version, date, commit, authors, reviewers).
2. Scope and methodology (STRIDE, tools, versions).
3. Summary of security architecture (one page).
4. Scan results summary: gosec, govulncheck, osv-scanner, Trivy, gitleaks, testssl (counts, links to raw reports).
5. Dependency and SBOM summary; accepted vulnerabilities with justification and expiry date.
6. Penetration test summary and remediation status.
7. Known issues and residual risks (table: ID, description, severity, mitigation, customer guidance), including at least: single-host key storage, platform compromise blast radius, license bypass, audit chain limits, clock heuristics, TOFU risk.
8. Customer hardening recommendations (host OS, disk encryption, firewall, `from=` restrictions, SIEM forwarding, backup storage off-host).
9. Security-relevant configuration reference and defaults.
10. Sign-off (developer, reviewer, date).

### 17.7 Pre-release checklist

- [ ] All CI gates green on the release commit (gofmt, vet, staticcheck, gosec, ESLint).
- [ ] `govulncheck` reports no reachable vulnerabilities; `osv-scanner` and `npm audit` show no High/Critical with available fix.
- [ ] Trivy image and fs scans clean of High/Critical with a fix; exceptions recorded with expiry.
- [ ] `gitleaks` clean on full history and release tarball contents.
- [ ] SBOM generated for binary and images and included in the package.
- [ ] Authorization matrix test passes for all routes; no route without declared permission.
- [ ] Secret-leak-to-log test passes including failure paths.
- [ ] Audit chain verifies after full E2E run and after backup/restore.
- [ ] Backup -> wipe -> restore -> verify test passes; installation ID and license preserved.
- [ ] Update test from previous release passes, including forced-failure rollback.
- [ ] Update script rejects tampered tarball and downgrade.
- [ ] License tests pass: forged, wrong installation, rollback, jump, expiry, grace, lock; lock mode leaves data and targets untouched.
- [ ] `licensectl` test vectors verify against the released binary; embedded public keys and key IDs match the vendor key register.
- [ ] No debug endpoints, pprof, test accounts, default passwords or sample keys in the build; the test-only "demo clock" build is never shipped (CI verifies its absence in the release).
- [ ] Security headers and CSP verified on all responses; `testssl.sh` grade A.
- [ ] Container inspection: non-root, read-only FS, dropped caps, no DB port published, images pinned by digest.
- [ ] Rate-limit, lockout, session, CSRF and OIDC test suites pass.
- [ ] MFA cannot be bypassed; wizard admin is local + MFA; recovery passphrase flow tested.
- [ ] Host key change blocks operations; platform key removal is refused (UI and API).
- [ ] Rotation failure-injection tests pass; incomplete rotation never removes old key.
- [ ] Nginx deploy fault-injection tests pass and restore original files.
- [ ] Azure least-privilege table matches the code paths actually exercised (mock and real suite run).
- [ ] Playwright E2E passes in English and Turkish; error messages contain no internal details.
- [ ] Penetration test findings High/Critical closed and re-tested.
- [ ] `SECURITY-REPORT.md` completed and reviewed; residual risks updated.
- [ ] Release notes list security fixes; advisory files updated in the package.
- [ ] `SHA256SUMS` signed offline with the release key; signature verified by `install.sh` on a clean machine.
- [ ] Customer documentation covers hardening, key backup, passphrase custody, and SIEM forwarding.
