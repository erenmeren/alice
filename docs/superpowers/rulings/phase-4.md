## Final review and fix wave

The whole-branch review was split into five areas (A1 root helper, A2 Nginx provider and SSH layer, B1 schema, inventory and certificate handling, B2 deployment engine, job system and wiring, C API and its seams with the web and the documents). None found a Critical defect. During the same days the owner's independent audit of 2026-10-04 (docs/security/reviews/independent-audit-2026-10-04.md, AUD-01..AUD-25) appeared in the working tree; its Phase 4 findings were taken into the same fix wave.

Found and fixed before the merge (findings P4-25..P4-50 in docs/security/reviews/phase-4.md carry the commits):

- A certificate or key path that resolves, through a root-owned symbolic link, to a name outside the helper's vocabulary was deployed and journaled, and the journal could not be read back: no status, no rollback, and cleanup deleted the only backup of the previous key (A1). Such a pair is now unsupported, the helper never writes a journal it cannot read, and cleanup keeps a journal it cannot read.
- `nginx-restore` answered "nothing was restored" after it had already put the certificate back (A1).
- `Conn.Run` could block forever when a managed server dropped or stalled the connection in the middle of a command; a deploy job would then never end and ignore cancellation (found twice: by a rare test hang, then by A2 for a deliberately stalling server).
- A scan of one server could replace the stored chain of an uploaded certificate, which was then deployed to other servers; and attaching a key to a certificate first seen on a server kept that server's chain for good (B1, W2 review, AUD-17). A held certificate's chain now comes only from a person; an incomplete chain can be completed by uploading the same certificate with its key and a complete chain.
- A deployment recorded as "failed, nothing written" could still be applied by a helper that started late, after sudo or PAM stalled (AUD-05). Recovery now fences the operation on the server (`nginx-fence`, helper protocol 5) before it records that nothing was written; the 60-second rule is gone.
- Alice down for longer than the helper keeps a committed journal (7 days) ended in "failed, nothing written" although the new pair was live (Task 24). A sent deployment without a journal after 24 hours is an unknown outcome.
- An error path of the engine could record "failed" for a deployment that may have been sent (B2; not reachable, now refused by the inventory unless nothing-written is proven).
- A recovering deployment was shown as "on hold for the license" when its original job was held (C); ALC-DEP-0020 said nothing had been put back when part had.
- Resource bounds missing against a hostile managed server: certificate pairs in a dump, dump warnings, RSA size and signature checks while reading certificate files, SSH-key discovery (users, files, keys, time), signing-request key generation (A2, B1, AUD-04, AUD-14).
- A connection dropped during the SSH handshake was reported as an authentication failure (AUD-10); the e2e stack published its unauthenticated test endpoints on every interface (AUD-07).

Rulings made in the fix wave:

- The fix wave was split into three implementers by package ownership (helper / SSH / provider / engine; schema / inventory / certificates / API / documents; web / e2e), each reviewed again by the reviewer of its area, until approved.
- The fence is a subcommand of its own with its own sudoers line — why: an existing subcommand taking a second meaning would be harder to reason about — cost: every managed server needs the new helper and the regenerated sudoers file before Alice talks to it again (`ssh.helper_outdated`).
- The helper refuses a new deployment over a pair whose latest operation was interrupted. When Alice no longer tracks that operation the engine restores it once and sends again once; a restore that put files back followed by a refused second send ends "rolled back" with its own reason and email (ALC-DEP-0024), and the expected file hash is never swapped — why: the operator's decision was made against what Discover showed — cost: one more Discover and deploy by hand.
- Alice restores a server-named operation only when it does not know the id or knows it as a deployment of that server and location whose outcome stayed unknown — why: a managed server must not be able to make Alice roll back a deployment Alice knows as finished.
- On attaching a key to a certificate first seen on a server, the certificate takes the uploader's chain even when the server's chain was complete — why: what Alice deploys is what a person gave it — cost: the uploader may have to upload the chain once more.
- Coverage floors were not lowered when the fix wave pushed three packages below them; tests were added for the new branches instead.
- Playwright retries a test once only when its failed attempt saw Chromium abort a request with `net::ERR_NETWORK_CHANGED` (the browser aborts every request in flight whenever any host interface gains or loses an address; there is no switch for it) — why: an environmental abort is not a product failure — cost: a product failure that coincides with such an abort is retried once and reported as flaky.
- The audit's findings in earlier phases and in process (AUD-01, 02, 03, 06, 08, 09, 11, 12, 13, 15, 16, 18–25) are not part of Phase 4 — why: they are in merged code or outside the code — cost: they stay open until the remediation pass that follows this merge.
