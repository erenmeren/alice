# Security Review — LDAP and Active Directory sign-in

Scope (plan `docs/superpowers/plans/2026-10-15-ldap-directory-signin.md`, "Review Focus" and rulings 1–12; spec
`docs/superpowers/specs/2026-10-15-ldap-directory-signin-design.md`): people signing in to Alice with the password of
an LDAP directory or of Active Directory over `ldaps://`. Migration `00015` (`ldap_directories`,
`ldap_group_mappings`, the directory columns of `users`, the service account secret key); the pure helpers
`internal/auth/ldap/ldapx` (filter and DN escaping, filter templates, transliteration, user names, unique ids); the
directory service and network client `internal/auth/ldap` (settings, secrets, the guarded `ldaps://` client, Test
connection, Test sign-in); `SignInLDAP`, `StepUpLDAP` and `RefuseLDAP` in `internal/auth`; 13 API routes
(`/api/v1/auth/ldap/*` public and session, `/api/v1/ldap/*` with `sso.manage`) with the per-name lockout
(`ratelimit.BoundedLockout`) and the refusal floor; the **Sign in to** selector, the directory step-up, the
**Directories** settings tab and the People & access changes in `web/`; the e2e fake directory
(`test/images/openldap`, compose service `fakeldap`).

**Not run by the author: a real Active Directory and Samba AD.** Every directory exchange ran against OpenLDAP 2.4.57
(the `osixia/openldap:1.5.0` image pinned by digest: the integration suite through `internal/testutil/fakeldap`, the
end-to-end journeys through the `fakeldap` compose service) or against the in-process mini server of
`internal/auth/ldap/mini_test.go`. Not verified: AD's in-chain matching rule `1.2.840.113556.1.4.1941` (OpenLDAP answers
it with no entries, and `TestGroupSearchTemplateWithDNAndNested` pins exactly that), the binary `objectGUID` from a real
AD (only `TestIdentityOf` with constructed bytes), AD's answers for disabled, locked and expired accounts (documented as
invalid credentials, sub-codes 533, 775, 532), AD's PDC forwarding of wrong passwords (the reason for the 1.5 s floor),
AD lockout thresholds and observation windows in a real domain, and AD Certificate Services chains.

## Method

Seven tasks on branch `ldap-signin` (from `main` 5c2272e plus the spec d0ea6bb and the plan 92c75cf), subagent-driven:
every task was implemented by one agent and reviewed by another that did not write it; Important findings went back
as fix rounds reviewed in scope (ledger `.superpowers/sdd/2026-10-15-ldap-directory-signin/progress.md`). Tests were
written with the code; implementers proved each safeguard load-bearing by mutation (removing the check, seeing the
named test turn red, restoring it): Task 1 six CHECK clauses, Task 3 ten mutations (M1–M10), Task 4 twenty-one plus six
in the fix round, Task 5 six plus six in the fix round. Rulings made during the work that change the plan: the per-name
limiter became a lockout (3 failures in 30 minutes lock the name for 45 minutes; replaces ruling 5); the step-up body
carries no user name (Alice stores the directory's sign-in name, `users.ldap_login`); `auth.ldap.denied` records the
typed name only for a resolved entry or `ambiguous_user`; a locked Alice account is refused in both MFA modes; a dummy
bind equalises unknown names; responses are capped at 8 MiB per connection and 5,000 values per attribute; every
refusal is held to 1.5 s.

## Open limitations

- **No real AD or Samba AD was run** (see the scope). The AD preset, the nested-group template and AD's account-state
  answers are documentation-based; the admin guide says so and asks customers to test with **Test connection** and
  **Test sign-in**.
- **Lockout DoS trade-off.** Anyone who reaches the sign-in page can lock a person's directory sign-in in Alice for 45
  minutes with three wrong passwords. This is deliberate (the alternative lets Alice lock the AD account) and is the
  same trade-off as AD's own lockout, but there is **no Administrator unlock path**: the lockout is in memory and only
  a restart clears it (`alice admin unlock` clears only Alice's own authenticator block). A full table (100,000 names
  still counting or locked) refuses names not yet in it until entries expire (30 minutes for a counting entry, 45 for
  a locked one).
- **In-memory limiter.** The lockout, the per-address limit and the floor are per process; a restart forgets them (an
  attacker who can restart Alice already controls the host).
- **No global cap on parallel directory sign-ins.** The per-address limit and the per-name lockout bound each source
  and each name, not the total load Alice can put on a directory (the same holds for the local sign-in and the OIDC
  start). An attacker with many addresses and many names can make Alice send many binds; each name still gets at most
  3 failures per 30 minutes.
- **Password copies that cannot be zeroed.** go-ldap's `SimpleBindRequest` takes a Go `string`, so the user's and the
  service account's passwords are copied into an immutable string and into the BER packet buffer for the bind; those
  copies live until the garbage collector frees them. Alice zeroes its own `secrets.Plaintext` copies and the request
  body buffer. The same limit applies to the OIDC client secret.
- **The directory password passes through Alice** (unlike OIDC). This is the cost of the feature; it is stated in the
  admin guide and the security overview.
- **MFA off is a one-factor sign-in.** An Administrator may switch Alice's authenticator off per directory; Alice does
  not check that the directory enforces anything instead.
- **Timing.** The floor equalises refusals that finish within 1.5 s; a directory slower than that (a timeout, an
  overloaded domain controller) is not held further, so its timing is visible, but it is then the same for known and
  unknown names.
- **AD-only behaviours not reachable in tests**: password expiry and "must change password" (AD refuses the bind; the
  person sees the generic refusal and must change it elsewhere), smart-card-only accounts, and fine-grained password
  policies.

## Findings

None open from this review beyond the limitations above. The decisions the final whole-branch review should look at:
the lockout DoS trade-off without an unlock path; that switching a directory off does not end its users' sessions at
once (OIDC behaves the same); that Test sign-in records the Administrator-typed test name even when the directory
finds nobody (an Administrator typing a password there would put it into the audit log, unlike the sign-in page).
